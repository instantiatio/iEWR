# Applications

iEWR helps turn an idea into a result you can check: an app or website, a study, a calculation, an engineering design, a method, or a new working arrangement. It can create new things and improve existing ones, from code and data to technical systems and organizations.

Start in ordinary words: “Build a website for this service”, “Investigate what is causing these deviations”, “Compare the upgrade options”, or “Help redesign this handoff”. The agent clarifies the task, organizes the work, selects methods, carries it out, and retains the context for continuation.

[Try iEWR →](/iEWR/eng/try/){ .section-action }

Below is a map of uses and possible results. Conditions sit alongside the tasks: some need only files and code, others need specialized tools, equipment, or participants. [Cases & Experiments](/iEWR/eng/cases/) records work actually performed and its checks.

End-to-end work spans clarification, a result agreed with the person, verification, and handoff. People set goals, make significant decisions, and accept results; available tools and authority define the execution boundaries.

## Apps, websites, and automation {#software}

**An assignment:** “Create a working website or application for this idea. Implement what it needs, check the result, and prepare it to run.”

- **A complete software product.** A working application or website, interfaces, tests, documentation, a build, and deployment. Scope, runtime, and acceptance criteria are defined for the task; checks include the intended conditions of use.

- **Improving existing software.** New features, fixes, refactoring, and dependency upgrades. Work starts from the actual system and includes checks of the effects of each change.

- **Automation.** Scripts, generators, converters, file processing, automated checks, and build procedures. Tasks with explicit rules and automatically checkable results are particularly suitable.

- **Data and integrations.** Data models, APIs, migrations, and integration code. Live integrations need the relevant access; the design accounts for repeated requests, concurrent operations, data history, and version compatibility.

- **Engineering documentation.** Requirements, scenarios, architecture and interface descriptions, and run and operating instructions. Documents are tied to the actual or proposed system and checked against it.

- **Architecture.** Alternative system designs, allocation of functions, components, interfaces, and reasons for the choice. The design depends on source information, constraints, and the necessary domain expertise.

The [GEO CRM case](/iEWR/eng/cases/geo-crm/) shows a connected application developed through successive assignments. [Try iEWR](/iEWR/eng/try/) includes a checked coding experiment with explicit expected results.

## Research lab {#research-lab}

**An assignment:** “Investigate this question. Examine the sources and data, identify hypotheses, and propose how to test them.”

- **Web research.** Source reviews, comparisons of approaches, and conclusions with their grounds and open questions. Available search tools provide access; provenance, reliability, and applicability of sources matter.

- **Investigating supplied materials.** A synthesis of documents, conflicting claims, recovered decisions, and conclusions about the question. Access to original materials and their context is especially useful.

- **Data analysis.** Prepared datasets, calculations, visualizations, analytical models, and reproducible reports. This needs source data and computing tools; causal conclusions require an appropriate research basis.

- **Experiment planning.** A research question, testable hypotheses, a plan, a protocol, and evaluation criteria. The plan connects possible outcomes to data that can actually be obtained.

- **Computational research.** Simulation, algorithm comparisons, numerical experiments, and sensitivity analysis. This needs a suitable computing environment and checks that the model represents the object of study adequately.

- **Physical and laboratory research.** Test programmes, equipment instructions, measurement processing, and conclusions. Running the experiment needs a laboratory, equipment, participants, and reliable measurements; a prepared protocol is a separate result.

## Decision engineering {#decision-engineering}

**An assignment:** “Compare the options against our goals and constraints. Explain the consequences and prepare a basis for choosing.”

Results can include alternatives, criteria, calculations, scenarios, and a recommendation with its grounds. The investigation shows what is known, what information is still needed, and what could change the choice. The person retains significant trade-offs and the final decision.

## AI-native engineering team {#ai-native-engineering-team}

**An assignment:** “Help organize the work across people and AI: define contributions, connect the results, and check them together.”

- **Joint engineering work.** Coordinated contributions from people, agents, and tools: roles, handoffs, checks, acceptance, and continuation. A team can start with one person and one agent; adding performers depends on the task and the agent environment.

- **Connected engineering results.** Traceable links between requirements, models, code, checks, and documentation. A system that automatically finds all consequences of any change needs explicit design of versioning, dependencies, and checks.

## Organizational engineering {#organizational-engineering}

**An assignment:** “Design the transfer of product support to another team. Define the roles, interactions, access, and readiness criteria.”

- **Systems of people, information, and technology.** A design for the joint work of participants, software, equipment, and suppliers. It accounts for connections between the parts; implementation needs the people responsible for processes and resources.

- **Organization design.** Allocation of functions and responsibilities, processes, interactions, and working conditions. The organization makes appointments, assigns authority, and changes actual working arrangements.

- **Putting changes into practice.** A pilot plan, participant training, and assessment of a new way of working. Implementation involves people taking action and observing effects over time.

## Method factory {#method-factory}

**An assignment:** “Find a way to solve this problem. Adapt an existing method or develop what is missing, check it on the task, and preserve what is useful.”

- **Method engineering.** Ways of doing the work, selection conditions, variants, and check results. The agent can find methods in professional sources, including the internet, reuse them, adapt them, and construct missing methods. Useful methods are retained in MethodPack with their grounds and conditions of use.

- **Domain Principle Frameworks — DPFs.** A connected system of patterns for recurring domain problems. FPF is already connected in 7.0.6: a separate DPF assignment invokes the original canonical method and assessment of both patterns and the package. Accumulating ordinary methods in MethodPack does not by itself produce a DPF.

- **Guidance and learning materials.** Guides, procedures, examples, exercises, and self-check tools based on sources and practical experience. Content applicability and learning outcomes are checked for the material’s intended use.

**AI is not limited to the starting repertoire of methods.** DMG covers finding, reusing, adapting, and constructing ways of working using FPF and the domain sources needed. You do not have to commission every new method separately. See [FPF, DMG & MethodPack](/iEWR/eng/foundations/methods/) and [DPF creation in 7.0.6](https://github.com/instantiatio/iEWR/blob/7.0.6/docs/DPF_CREATION.md).

## Physical products and operations {#physical-engineering}

**An assignment:** “Prepare a component design: its model, calculations, documentation, and test plan. Identify what manufacture and verification will require.”

- **CAD modelling.** Parametric parts and assemblies, drawings, and specifications through a connected CAD tool. Checks cover geometry, constraints, assembly, and export.

- **CAE and engineering calculations.** Analysis models, loads, results, and their range of applicability. This needs specialized tools and engineering expertise that connects the calculation to the physical product.

- **BIM and infrastructure.** Models of assets, equipment, utilities, diagrams, and documentation. Work depends on tools, formats, and data completeness; checks cover consistency between models.

- **Physical product design.** A design, models, calculations, bills of materials, and manufacturing and test plans. The full cycle also needs production, measurements, and physical verification with the relevant participants.

- **Operations support.** Diagnosis, log analysis, repair recommendations, and authorized operations followed by checks of recovery. Actions on a live system require a connection and the relevant authority.

- **A digital twin with feedback.** A model updated from observations, producing predictions that can be compared with reality. This needs an ongoing data supply, synchronization, maintenance, and evidence that the model is suitable for the intended decisions.

- **An engineering cycle with physical equipment.** A prospective scenario: develop a variant, manufacture it or run an experiment, measure, and refine. Implementation needs connected equipment, organized actions, and verification of physical results.

## Self-developing engineering environment {#self-developing-engineering-environment}

**An assignment:** “Investigate this difficulty in iEWR’s own behavior, improve the way it works, and check the change.”

iEWR itself can be the subject: instructions, navigation, methods, architecture, and supporting tools. You set the goal and scope; the agent investigates, changes, and checks the environment using its own engineering means. A project method can also improve during an ordinary assignment. Changing the environment itself starts with a human instruction; see the [7.0.6 self-development procedure](https://github.com/instantiatio/iEWR/blob/7.0.6/docs/SELF_DEVELOPMENT.md).

## Context that supports continuation {#continuation}

Source materials, decisions, results, checks, and unfinished work are retained in the project folder. A later session uses them to recover the basis for the work. In GEO CRM this supported continuation along Codex → DeepSeek Harness → Codex, followed by guides to the system that had been built.

You can assign a specific result, think through a question together, or ask “What can you do?” and “How can we continue this project?”. [How iEWR works](/iEWR/eng/how-iewr-works/) explains the environment and its working arrangements.
