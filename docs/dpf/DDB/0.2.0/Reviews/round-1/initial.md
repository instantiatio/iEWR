# Первоначальное восстановление DDB 0.2.0

Основа: только DDB-REQUEST.json, REVIEW_PROTOCOL.md, полный DDB 0.2.0 и README текущей редакции. SHA256 DDB совпал с REQUEST: fb98104985118319d0fd398a082ac32fb9ff8bdd6dc864be5f7dd7990f05420c. Другие DPF, история, predecessor, CHANGES и оценки до этой записи не читались. Первичные внешние источники не читались; предметная реализация ещё не выполнялась.

Назначение: подготовленный разработчик с обычным SQL и способностью проверить небольшой запрос/процедуру проектирует данные транзакционного прикладного сервиса: смысл факта, схема, конкурентное изменение, чтение, история и эволюция. Достаточную готовую модель можно принять вместо полного прохода.

Первый полезный результат задачи — компактная модель фактов и инварианта, а не немедленно выбранная СУБД. По DDB.1 я различаю ресурс с доступным остатком 5, резерв одной логической операции с requested_qty=accepted_qty=4 при успехе и явным отказом без резерва иначе, а также сохранённый результат операции и историческую цену подтверждения. Нужны идентичность ресурса, principal и логический ключ операции, граница их уникальности/повторного использования, единица количества/цены и момент фиксации цены. Текущая цена каталога и подтверждённая цена — разные факты. Предположение локальной атомарной БД далее условно; внешняя оплата в задании не установлена.

Далее DDB.2: схема Resource(resource_id,remaining), Reservation(reservation_id,resource_id,qty,unit_price_at_confirmation,operation_identity), Operation(principal,key,payload,result). Ключи, FK, NOT NULL и qty>0 задаются явно; операция имеет уникальную логическую идентичность. Инвариант: сумма действующих резервов плюс remaining равна исходному запасу, remaining>=0; частичная выдача недопустима. Полный жизненный цикл отмен/пополнений требует дополнительных правил, если они входят в сервис.

DDB.3: условное уменьшение remaining на 4 при remaining>=4, создание резерва и сохранение результата должны завершаться одной транзакцией; при нуле изменённых строк — отказ по установленному контракту. Два разных ключа соревнуются за ресурс: допустимы один резерв 4, один отказ и остаток 1. Защита только operation_key этой гонки не решает. Для одинакового principal/key сравнивается payload: тот же смысл возвращает сохранённый результат, иной отклоняется; одновременному дублю нужен путь ожидания/сверки. Ответ, потерянный после commit, не разрешает второй эффект. TTL ключа ограничивает гарантию позднего повтора. Ошибку СУБД/конфликт отличаю от отказа по запасу; повторяю нужную транзакцию целиком только в пределах выбранного контракта.

Дальнейшая проверка: выбрать СУБД/версию и подтвердить её механизм, учесть всех writers; проверить две независимые операции по 4 из 5, одновременный дубль, иной payload, сбой до и после commit, состояние остатка/резерва/результата; изменить цену каталога и проверить прежнюю цену подтверждения. DDB.5 задаёт исторический факт и проверку цены; асинхронная проекция пока не нужна. DDB.4 нужен при определённом запросе/нагрузке; DDB.6 — при изменении работающей схемы, с учётом смешанных версий и новых записей после snapshot. Для первого результата эти два метода не являются обязательной подготовкой.

Остановка/уточнение: до реализации неизвестны СУБД, контракт идентичности/срока повтора, точный момент и источник фиксируемой цены, права и среда проб, другие writers и необходимость внешних эффектов. Можно передать условную модель и проверочные последовательности; нельзя утверждать backend correctness, production readiness, измеренную производительность или успешное recovery. Это восстановленная инструкция и конструктивный набросок одного AI-читателя, а не выполненный тест, человеческое испытание или статистическая независимость.
