# R — восстановление execution basis

Вход через C только по explicit continuation/re-entry use. Сначала bound project
history: 0 инициатив — обычный новый вопрос; 1 — direct carrier; несколько —
Human selection. Не включать package/frozen/source или candidate evidence в
project history. STATE_INDEX — необязательная подсказка; invalid/stale/conflicting
index игнорируется. Не создавать новую initiative от наличия scaffold.

Восстановить масштаб текущего поручения: уже полученный промежуточный результат
может быть достаточен для своей части, пока другие необходимые части остаются.
Передать caller пригодные результаты, оставшиеся зависимости, действующие direct
grounds и факты effects, чтобы продолжение не требовало повторного «продолжай».
Запрос статуса сам не отменяет поручение; его изменение сверяется с direct Human
словами. Возврат R не разрешает actuation, завершённое/unknown не повторяется.

Нужные редакции и существенные ответы должны быть доступны следующему участнику
по [общему порядку файлов](../../project/README.md). Пригодность существующей
истории проверяется по его доступу и нужному периоду; память текущего чата не
доказывает восстановимость. Сохранить недостающее до зависимого use через owning
X/G/E basis; R остаётся query. Не дублировать пригодную историю и не обходить весь
проект ради каждой правки; новые STATE/registry не требуются.

`reconstruct` получает только AccountQuery.read: G direct relations, S/F/X/E
relied bindings и X/E factual records. Каждое представление сохраняет exact refs
и digest. Два чтения обнаруживают часть concurrent changes; они не доказывают
глобальный atomic snapshot или отсутствие ABA/непроверенных surfaces. При
material concurrent writer требуется stronger substrate либо affected hold.

Оригинал direct relation остаётся у своего owner/SoR. R не принимает решение об
impact вместо subject owner: `depends / mentions only / unresolved` и unsearched
surfaces передаются с basis. Он возвращает demand через C, а новый observation,
reconciliation, repair или retry получает отдельные X/G/E основания. Unknown
эффект удерживает зависимый use даже при похожих конечных bytes. Idempotency key
не доказывает exactly-once чужого провайдера.

Сохранять три accounts раздельно. Selection successor на safe boundary —
derived result с explicit basis, не actuation/activation. Исторический Work,
Method/plan/source/configuration и decision не переписываются. Старые B1/B2 JSON
owner records и schema 1/2 navigation carriers читаются в исходных meanings;
неизвестная версия удерживает dependent continuation. Текст legacy carrier
возвращается exact UTF-8 с hash для bounded Human/agent interpretation; по имени
Loop/Task/Run/admitted новые semantic claims не создаются.

## Ожидаемые решения

При handoff восстановить для каждого существенного ожидания exact вопрос и
редакцию, адресата/decider, требуемый ответ/данные, условия, известный срок и
зависимое действие. Различать ответы разных участников и ещё не завершённые
формы. Сохранить уже разрешённое независимое продолжение. Pending request,
полученный ответ и фактически применённый ответ — разные наблюдения. Repeated
delivery и неизвестный эффект не replay; для current use вернуть G/X exact
изменение/отзыв и восстановленные effects. R не возобновляет actuation сам.

При нескольких ожиданиях восстановить выбранный охват, момент снимка и
непрочитанные/недоступные источники. Отдельно вернуть готовые вопросы,
недостающие входы/адресатов, ответы с непроверенными условиями и конфликтующие
либо устаревшие основания. Сохранять ID + редакцию, direct refs/digests, вклад
каждого участника, основания сроков/порядка, все необходимые зависимости и
разрешённое независимое продолжение. Роль PO/DE/QA не заменяет decider/authority;
получение одного ответа не закрывает остальные необходимые условия действия.

Условия связывать с владельцем проверки, критерием и evidence; ответ, отзыв,
interpretation и фактическое применение не сливать в одно состояние. Последний
файл или строка «применено» не выбирают действующее основание. Unknown effect
возвращает потребность в сверке, а не повтор исполнения. Частичный охват, цикл
или отсутствующая зависимость остаются видимым пробелом для затронутого use.

Необязательный список по [I](../interaction/DECISION_VIEW.md#несколько-ожидаемых-решений)
готовится из этих сведений по запросу/возврату к выбранной работе или при
существенном изменении зависимостей в активной сессии. Список не заменяет три
accounts и owner records, не обнаруживает отзывы вне доступных источников.
Даже новый снимок требует current-use сверки. При отказе renderer достаточно
текста/отдельных вопросов; старые снимки, ответы и effects сохраняются.
