# Развитие самого iEWR

Применять только когда текущий Human запрос явно поручает изменить **сам iEWR**:
его bundled DPF, modules/adapters, способы работы или архитектуру. Упоминание
iEWR, найденная ошибка, обычная разработка пользовательского продукта, direct
source use и project DPF registration этот scope не включают. Наблюдение может
обосновать предложение улучшения; оно не разрешает его реализацию.

Это instruction-led поддержка применимых S/F/G/X/E/L/R/C/I/P, а не новый owner,
runtime route, scheduler или универсальный lifecycle. Наличие файла не добавляет
процедур к обычной задаче. Использовать только действия, нужные текущему результату.

## Начало и возобновление

1. Установить exact изменяемый продукт и current question/receiving use.
   Достаточно обычного поручения с целью, входами и границами; уточнять лишь
   условия, меняющие решение. Сформулировать наблюдаемые критерии и поддерживаемые
   варианты, включая ordinary-task non-interference, когда меняется общий entry.
2. Восстановить [три accounts](../recovery/CONTRACT.md): current direct grounds,
   relied execution basis и factual effects. Проверить baseline ZIP/manifest и
   исходное соответствие рабочего дерева. Handoff читать по вопросу in-place,
   сохранять exact archive/member/digest; старые scripts/grants не исполняются.
3. Различить **принятый baseline**, **изменяемую конфигурацию** и **используемую
   для разработки basis**. Сохранить исходный ZIP либо иной authoritative exact
   snapshot. Не переносить acceptance на новую конфигурацию. При trial новой
   инструкции назвать её revision/digest и affected use до применения; остальные
   governing grounds сохраняются. Редактирование инструкции само её не активирует.
4. Переиспользовать достаточный result/Method. WorkPlan нужен для фактической
   координации intended work, а не из-за размера задачи. Не создавать полный
   набор ТЗ/ConOps/SysReq/шаблонов без decision-changing gap.

Для прерываемой доработки использовать существующий authoritative record;
если его нет, достаточно одного `project/artifacts/process/<initiative>/` locus.
В читаемом файле сохранить request/границы и criteria; identities трёх basis;
обоснование выбранного изменения и alternatives; exact проверяемый subject;
observations/checks/effects и текущий stop/следующий уже разрешённый шаг.
Ссылаться на direct owner/SoR вместо дублирования его records. Имена файлов и
формат не обязательны; отдельные документы появляются только для нужного use.
Пустой scaffold не initiative. Несколько реальных initiatives требуют выбора
Human; после interruption сначала сверить effects, unknown не replay.

## Выбрать и реализовать изменение

| Предмет | Минимально нужная поддержка |
|---|---|
| Bundled DPF | [DPF refresh guide](../../docs/BUNDLED_DPF_BASELINE_REFRESH_AND_INTEGRATION_GUIDE.md): pinned sources/author edition/revision/digests, лицензии, claim delta, affected uses, actual contribution и package integration |
| Modules/adapters | Exact consumer/port behavior до/после, current host controls, разрешённые effects; regression на affected seam и отказ/partial/unknown. Не ослаблять controls ради passing test |
| Method/instruction | Named task и gap, adequate existing route либо candidate change; проверяемая гипотеза, representative/discriminating use по живому риску; result/description/coherence/fit/effectiveness — разные claims |
| Architecture | Назвать old/new governing obligation, причину и последствия, альтернативы, затронутые consumers, migration/recovery и evidence; существенный пересмотр предъявить для **отдельного Human решения до зависимой реализации** |

При source update одинаковая авторская дата с иными bytes — новая explicit
revision binding либо unresolved drift. Не переписывать same identity/edition
под новым digest. Сохранять author date, pinned commit и локальный revision ID
раздельно. Новый repertoire меняет доступный состав, не прошлую relied basis.

Сравнивать варианты по одним критериям. Выбирать достаточно компактный способ;
обосновать каждый добавленный механизм/документ текущей потребностью. Source
contribution должен менять действие, criterion, решение или stop; чтение названия
и hash не application. Applicable DPF выбирать через S → F без namespace routes.
Ссылки на FPF не требуют его загрузки/полного чтения: действует [S policy](../sources/GUIDANCE.md).

Перед material effect действуют current G permission/authority, capability,
allowed/prohibited scope, [E controls](../effects/GUIDANCE.md) и recovery/stop.
Несколько локальных действий внутри данного scope не требуют microapprovals.
Changed material scope/commitment требует решения только затронутой части.

## Проверить изменение и обнаружить дрейф

До trials назвать claim, exact configuration, вход, expected observable
criterion, permitted effects и предел evidence. Выполнить необходимое реальное
действие, сохранить commands/outputs и before/after; walkthrough, deterministic
fixture, actual agent trial и review не подменяют друг друга. Не считать
ретроспективно подсказанный ответ самостоятельным discovery.

При изменении описания различать содержание и форму. Добавленное условие или
отношение — content delta. Если от form claim зависит выбор, сначала сравнить
старое и уточнённое содержание в одной форме, затем одинаковое уточнённое
содержание в разных формах, сохраняя условия, unknown и основания. Выбрать
минимальный informative contrast: прямой сверки утверждений достаточно, когда
она разрешает вопрос; дополнительный контраст нужен лишь для отдельной гипотезы
об их совместном влиянии. Не вводить обязательную matrix или experiment для
каждой правки; несколько agent probes не доказывают удобство для человека.

Если обещается работа без этой переписки, проверить чистую selected поставку
агентом без development/chat history: ordinary request → shipped entry → result,
effects и достаточный stop. При проверке самостоятельного выбора не подсказывать
DPF/PatternID, ожидаемый ответ или маршрут. Для actual trial задать только
пользовательские входы, разрешённый root/effects и доступные инструменты.
При недоступном независимом trial честно удержать именно это обещание.

Ordinary-task controls подбирать по изменённому entry: например, обычная правка
пользовательского файла и direct DPF use/registration. Упоминание iEWR как
инструмента не должно запускать этот guide, менять продукт, требовать acceptance
package или записывать саморазработку. Проверить это наблюдённым поведением.

Сравнить весь selected delta с accepted baseline и intended scope. Проверить
Core/owner boundaries, import DAG, source identities, совместимость consumers,
документацию/каталоги и чистоту состава. Изменение hashes само не обосновывает
delta; сначала объяснить каждую material правку, затем обновлять inventory.
Stale hashes, неизвестная правка, changed basis или unknown effect удерживают
dependent use до reconciliation. Failed attempts сохранять; исправлять и
перезапускать только affected criterion, сохраняя новый exact tested subject.

Formal Work/Method claims требуют собственных оснований по
[execution basis](../execution/EXECUTION_BASIS.md); файл, план, probe и PASS их
не устанавливают. Host skips не закрываются weaker shim или Human acceptance.

## Подготовить exact результат для Human

Сначала выполнить уже разрешённые edits/checks и собрать candidate ZIP. Решение
принимается по конкретным bytes: acceptance не является разрешением начать их
подготовку. Согласовать version/status, README, configuration и manifest; major
change обосновать по contract compatibility, а не по размеру текста.

Из корня продукта, используя Python 3.10+ в проверенном cooperative local host:

```text
python -B tools/package/verify_configuration.py --root .
python -B tools/package/prepare.py check --root .
python -B tools/package/prepare.py diff --root . --baseline project/source/iEWR-previous.zip
python -B tools/package/prepare.py build --root . --output project/artifacts/iEWR-candidate.zip
```

Подставить реальные пути. Helper использует только явно выбранный manifest,
не добавляет обнаруженные user files, не обновляет hashes, не выдаёт permission
или acceptance. Output должен быть новым; старую поставку не перезаписывать.
Portable check — отдельный compensated maintainer consumer, не qualification
POSIX adapter на Windows. User inputs/evidence из project/ не входят в продукт;
его поставляемый [scaffold](../../project/README.md) ограничен exact allowlist.

Предъявить: описание before/after; причины и unresolved alternatives; exact
sources/licensing и useful contributions; checks с failures/skips/limits;
архитектурный delta и version rationale; ZIP/manifest/configuration SHA-256;
effect reconciliation и что именно предлагается принять. Evidence хранить
рядом с поставкой, вне product payload. Проверить ZIP inventory/CRC/digests и
packaged links, не полагаться на соседние development files.

Human response сохранять с exact subject/use/conditions. Если после предъявления
bytes изменились, прежнее решение не покрывает новый предмет автоматически.
Для принятия и последующей передачи использовать проверенный ZIP без пересборки;
отдельно записывать observed acceptance. Publication — отдельный effect scope.

## Сохранить полезный опыт и завершить

Из фактического случая извлечь только нужное следующему maintainer: условие,
наблюдение, изменение способа, подтверждающий test/пример и предел переноса.
Наблюдение, proposal, tested support и принятое правило сохраняют свои основания;
один успех не становится универсальной policy. Переиспользовать
[краткий опыт](EXPERIENCE.md), добавляя туда только устойчивый полезный вывод
с provenance, когда его inclusion входит в текущее поручение.

Закончить на adequate result и reconciled material effects либо honest affected
blocker. Lessons не запускают successor, review, Admission или следующую
инициативу. Следующий explicit запрос вновь передаётся C.
