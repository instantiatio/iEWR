# L — evidence, decision и actual reliance

Result сохраняет direct domain/FPF kind. Candidate допустим как presentation
unresolved intended reliance, не обязательный новый type/status.

`assess_receiving_use` получает exact subject/digest/use/criterion и direct
evidence. Verification demand появляется лишь при owner-bound Method/use/DPF/
LPF/policy/assurance need. Без trigger не появляется job. Verification Method,
performed Verification, observations/result, assurance, компетентный review,
authority decision и observed reliance остаются разными facts. L не вызывает
X/E actuation; demand возвращается C и owning use отдельно задаёт execution.

Для порученного проектирования/реализации основание соразмерной проверки
устанавливается по нужному использованию и существенным свойствам результата
через [F](../formation/DOMAIN_WORK.md#качество-проектируемого-и-реализуемого-результата).
Пользователь не обязан отдельно запрашивать такую проверку. Это не создаёт
универсального Verification job: пригодное имеющееся evidence достаточно,
новое действие выполняется через существующих owners только по нужному вопросу.
Сопоставлять критерий с фактическим результатом для exact предмета и условий.
Различать «подтверждено в этих пределах», «выявлен дефект» и «не проверено»;
отсутствие наблюдения не pass. Синтаксическая/структурная проверка, правильность
предметного смысла и пригодность в сценарии использования не подменяют друг друга.
Полнота согласованного scope и корректность реализованного — разные свойства.
При наличии перечня обязательных результатов нужен достаточный ответ о покрытии
по F; количество PASS не заменяет сверку с этим перечнем. Один подходящий
набор checks может дать оба ответа без отдельного Verification job.
Согласие Human, выбранный DPF, план теста и успешный tool call сами не доказывают
технического свойства. После исправления пересматривать затронутые проверки,
сохраняя достаточные незатронутые evidence; общее «всё проверено» без охвата недопустимо.

Evidence/review не grants. Решение на use A не покрывает B или новую
configuration. Current source/basis comparison переоткрывает affected use;
mentions-only и unsearched surfaces не превращаются в независимость.
Material durable effect с unresolved disposition удерживает только dependent
closure/use. External authoritative SoR не копируется в Git ради ceremony.

Для файлов соблюдать [связь проверки с редакцией](../../project/README.md):
состояние и проверенное свойство должны быть различимы и доступны для use.
Исправление сохраняет старую проверку как факт о прежнем предмете; пересматривается
лишь затронутое, unresolved dependency не считается независимостью. Hash без
доступного экземпляра недостаточен; повторная сборка не тот же проверенный ZIP.

`observe_reliance` хранит только direct observation конкретного receiver/use,
не автоматическую запись из assessment/decision. Observation ref ссылается на
actual use; переданный текст не доказывает факт сам по себе. No current adequate
result/no evidence — named gap, no universal Admission escalation.

Для Human–AI проверки различать своевременность решения, восстановимость
решающих оснований и фактическое применение ответа. Проверка формы или agent
trial не доказывает понимание человеком, экономию его времени или причинный
эффект. Сравнение требует одинаковых результата, модели, reasoning effort,
инструментов и существенных входов либо явного ограничения атрибуции.
Человеческая нагрузка включает понимание, ожидание, уточнения, исправления
и перенос затрат на других участников; число gates само по себе не качество.
