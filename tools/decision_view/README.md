# Компактный Decision View

Каркас для отдельного вопроса человеку: один автономный HTML с содержанием и полями ответа. Выбор и подготовка содержания — по [I](../../modules/interaction/DECISION_VIEW.md). Для достаточного ответа в разговоре файл не нужен. Вложения, сервер и браузерные библиотеки не требуются; материалы открываются по ссылкам.

Это композиция [Human Views](../../modules/interaction/HUMAN_VIEWS.md) с отдельным
контрактом ответа. Пять [композиций для чтения](../human_view/README.md) используют
ту же визуальную основу без Answer. Прежние JSON/CLI и сохранённые вопросы/ответы
совместимы; новый стиль применяется только к новым HTML.

## Быстрый пример

Из корня распакованного iEWR:

```sh
python3 -B tools/decision_view/build.py tools/decision_view/examples/question.json project/handoff/example-question.html
```

Открыть `project/handoff/example-question.html` обычным браузером как файл. Учебный пример создаст также ER-представление в `project/handoff/decision-view-materials/`. Ответ сохраняется кнопкой в `example-answer.html`; браузер выбирает папку скачивания. Вернуть этот файл в задачу явным сообщением. `page.html.in` — исходник каркаса, его не открывают как готовый результат.

Требования к сборке: Python 3.10+; для непосредственно связанных Markdown — также Node.js 20+. Marked включён в комплект с MIT-лицензией, установки пакетов не требуется. Готовые HTML читаются без этих инструментов и без сети. Для заполнения/скачивания ответа нужен JavaScript; сохранённый ответ читается и без него. Файловый режим проверяется в обычном браузере; поведение встроенного предпросмотра конкретного host может отличаться.

## Подготовить вопрос

В JSON указать `questionId` (предмет и редакция), `kind`, `question`, `subject`, `recipient`, `recommendation`, `waiting`. Пример показывает остальные поля. Три варианта `kind` меняют подачу оснований: `short-decision`, `comparison`, `acceptance`. Пустые разделы не добавляются. `options` может содержать любое число реальных альтернатив или отсутствовать — свободный ответ всегда доступен. `decisionRequired:false` не создаёт файл.

Дополнительно: `why`, списки `basis`/`limits`, `table` с `title`/`columns`/`rows`, `sections` с `title`/`text`, `details`, `materials`. Текст отображается как текст; произвольный HTML не исполняется. `synthetic:true` помечает учебные данные. Существенные ограничения, рекомендация и последствия остаются на основной странице. Использовать читаемые блоки без требования одного экрана; число экранов не заменяет достаточность содержания.

Необязательный `attention:{mode,reason}` показывает GLANCE / STANDARD / DEEP и
причину глубины. DEEP первоначально раскрывает `details`; в других режимах они
доступны через раскрытие. Основания, limits, варианты и последствия не скрываются.
Если поле отсутствует, прежняя механика сохраняется. Режим не обещает время чтения.

Числовые `parameters` имеют `id`, `label`, `unit`, `min`, `value`. Изменённые условия сохраняются точно, но каркас не пересчитывает модель: зависимый расчёт выполняется отдельно. Если допустим вариант пересчёта, его ID задаётся как `parameterChangeChoice`; иначе при изменении параметров использовать свободный ответ.

Для материала нужны `path`, `filename`, `title`, `revision`, `role`, `linkPurpose`; необязательный `sha256` фиксирует ожидаемый исходник. Локальный путь считается от JSON, а в готовом HTML пересчитывается относительно вопроса. Отсутствующий файл или несовпадающий digest останавливают сборку. `role:decision-evidence` показывает предел независимой проверки при недоступном материале. Внешние HTTP(S)-ссылки сохраняются без загрузки и проверки.

## Дополнительные представления

Сначала выбрать достаточный основной каркас. Если отношения, геометрия или сценарии в нём плохо различимы, добавить отдельное представление с конкретным вкладом и ссылкой с основной страницы. Не создавать универсальную библиотеку приложений к каждому вопросу.

| Вход в `materials` | Подготовка |
|---|---|
| Локальный `.md` | Статический HTML для чтения; исходник сохраняется. Глубокие MD-ссылки помечаются «исходник MD», рекурсивной конвертации нет. |
| Локальный `.er.json` | Проверка структуры модели и ER-схема SVG внутри автономного HTML: сущности, поля, PK/FK/UK, кратности, таблица связей, масштаб/прокрутка. |
| `.zip` | Сначала раскрываются имя и известный размер, затем отдельная ссылка скачивания. |
| Готовый HTML, SVG, PDF и другие материалы | Обычная ссылка; пригодность формата проверяет автор. |

Производные страницы имеют имя с digest и переиспользуются при совпадении содержания. Они не вложены в вопрос. Если вопрос перенесён и относительная ссылка больше не работает, рядом остаётся сообщение с точным именем файла/редакцией и просьбой запросить материал у Developing Engineer. Браузер не всегда позволяет автоматически установить отсутствие локального файла; условное сообщение не выдаёт предположение за факт.

Новые HTML записываются точными байтами UTF-8 без системной замены переводов
строк. SHA-256 и размер относятся к фактически сохранённым файлам, включая
повторно используемые прежние представления Windows. Старые вопросы и ответы
не переписываются: исправление сборщика не исправляет их прежние метаданные.
Если старый вопрос содержит неверный хеш, сохранить его и ответ, сверить
конкретный материал и разобрать расхождение отдельно; новая редакция вопроса
не наследует согласие автоматически.

Markdown reader показывает заголовки, списки, таблицы и код. Raw HTML экранируется, изображения заменяются подписями; Mermaid внутри Markdown остаётся кодом. Если изображение или диаграмма меняют решение, дать отдельное подготовленное представление. Автоматического распознавания ER из текста, SQL или Mermaid нет.

ER-модель имеет `schema:1`, `title`, `revision`, `entities` и `relationships`; точный пример — [orders.er.json](examples/orders.er.json). У сущности уникальный ASCII `id`, необязательный `label`, атрибуты `name`/`type`/`keys`. В связи нужны `from`, `fromAttribute`, `to`, `toAttribute`, `fromCardinality`, `toCardinality`; допустимы `1`, `0..1`, `1..*`, `0..*`, `?`. Кратность у конца означает число объектов этого конца на один объект противоположного. Неизвестное указывать `?`. Неподтверждённое не достраивать по догадке.

ER renderer ограничен 50 сущностями, 100 полями на сущность и 200 связями; это предел входа, не гарантия читаемости плотного графа. Для сложной модели выделять нужный фрагмент или использовать другое представление. Он не подключается к БД, не проверяет SQL/миграцию/смысл ограничений. Самостоятельная команда: `python3 -B tools/decision_view/er.py model.er.json diagram.html`.

## Список ожидаемых решений

`pending.py` создаёт необязательный статический список для выбранных ожиданий.
Для одного простого вопроса использовать обычный разговор или каркас выше.
Вход готовит вызывающий агент по [I](../../modules/interaction/DECISION_VIEW.md#несколько-ожидаемых-решений)
и восстановленным owner records. Порядок и его объяснение задаются во входе,
сборщик их сохраняет. Автоматического поиска вопросов, оценки authority,
отправки, общего ответа, исполнения и фонового обновления нет.

```sh
python3 -X utf8 -B tools/decision_view/pending.py project/artifacts/pending.json project/handoff/pending-1.html --root .
```

Python 3.10+, только стандартная библиотека; Node и JavaScript не нужны.
`root` — корень выбранного iEWR-проекта. Вход и локальные ссылки находятся
внутри него; результат — новый `.html` в `project/handoff/` или `project/artifacts/`.
Каталог результата уже должен существовать. Запись exclusive, без перезаписи.
Нужный новый снимок получает другой путь; старые вопросы/ответы остаются доступны.
Правило числовой версии выпуска продукта не требует менять номер iEWR для снимка.

Минимальный учебный вход (с намеренно неизвестными основаниями):

```json
{
  "schema": 1,
  "scope": "Учебная выбранная задача; не действующее поручение",
  "asOf": "2026-09-19T18:00:00+03:00",
  "coverage": {"sources": [], "omissions": ["История проекта не проверена"]},
  "items": [{
    "id": "Q-1", "revision": "1", "subject": "Выбрать допустимый компромисс",
    "question": null, "role": "Product Owner", "decider": null,
    "contribution": "Определить допустимую потерю в результате",
    "gateBasis": null, "authority": null, "state": "needs-recipient",
    "missingInput": ["Не установлены участник и его полномочия"],
    "answerBy": null, "deadlineBasis": null, "validUntil": null,
    "priorityReason": "Порядок не установлен; пока один вопрос",
    "dependsOn": [], "externalDependencies": [],
    "dependentActions": ["Применить выбранное изменение"],
    "independentWork": [], "response": null, "conditions": [],
    "revocation": null, "effects": [], "sources": [],
    "refreshWhen": "После установления адресата и прямых оснований"
  }]
}
```

Все показанные поля обязательны; неизвестное обозначается `null` или явно
описанным пробелом, пустой список означает отсутствие записей **в проекции**.
Неизвестные/повторные поля JSON, неверный тип и дубли ID + revision — ошибка.
Вход UTF-8 до 1 MiB, максимум 100 вопросов, в каждом списке до 100 элементов;
одна строка до 12000 символов. Читаемый локальный источник — до 32 MiB.
Неизвестная версия схемы не интерпретируется по догадке.

| Поля | Смысл |
|---|---|
| `scope`, `asOf`, `coverage` | Выбранные задачи/получатель, время подготовки с часовым поясом, `sources` и `omissions`. Пустая выборка не доказывает отсутствие ожиданий. |
| `id`, `revision`, `subject`, `question` | Стабильная пара ID/редакция, краткий предмет и ссылка на сохранённый вопрос. Сортировка не перенумеровывает вопросы. |
| `role`, `decider`, `contribution`, `gateBasis`, `authority` | Роль для навигации, конкретный участник или null, нужный вклад и отдельные ссылки на основания. Сборщик не выводит полномочия из роли. |
| `state`, `missingInput` | Оценка составителя: `ready`, `preparing`, `needs-recipient`, `conditions`, `conflict`, `closed`. Последнее означает применено либо отказано по указанным фактам, а не разрешение действия. |
| `answerBy`, `deadlineBasis`, `validUntil`, `priorityReason` | Раздельные сроки ответа и действия основания (ISO-дата/время с поясом или null), ссылка на основание срока и текст причины порядка. Истекшие к `asOf` сроки помечаются; часы/таймер не запускаются. |
| `dependsOn`, `externalDependencies` | Локальные prerequisites как `{"id":"Q-1","revision":"1"}` и внешние ссылки. Все действительно необходимые условия — AND. Циклы и отсутствующие строки видимы; даже `closed` не доказывает удовлетворение зависимости. |
| `dependentActions`, `independentWork` | Текст зависимых действий и уже разрешённого независимого продолжения по основаниям составителя; это не команды. |
| `response`, `conditions`, `revocation`, `effects` | Ссылка на точный ответ, условия, отзыв и список ссылок на фактические эффекты. Отсутствие ответа не отказ, отсутствие отзыва не доказательство его отсутствия. |
| `sources`, `refreshWhen` | Ссылки на основания строки и условие обязательной сверки/нового снимка. |

Каждая ссылка имеет ровно `label`, `path`, `sha256`: понятное имя, путь
**от входного JSON** и ожидаемый SHA-256 в нижнем регистре. `path:null` обозначает
недоступное локально основание, `sha256:null` — неустановленный digest. Можно
использовать `../` внутри выбранного root. URL, абсолютные пути, fragment/query,
процентное кодирование пути, символы управления, symlinks/reparse points не
поддерживаются. Внешний SoR обозначается именем с `path:null`; сеть не используется.
Отсутствующий файл или несовпадение digest показываются как пробел с именем
источника; действующего разрешения из такой строки не следует.

Условие имеет `text`, `owner`, `criterion`, `evidence`: точный существенный текст,
владелец проверки и критерий (строка/null), список ссылок на evidence. Ответ,
условия, отзыв и фактические эффекты видны на карточке без раскрытия подробностей.
Прежние `Question`/`AnswerDraft` не изменены; выдумывать `valid_until` для reader
нельзя. Список не интерпретирует слова человека и не проверяет удовлетворение
условий/AND вместо G/X/E.

Структурная ошибка останавливает подготовку до записи. Повторное чтение источников
выявляет часть изменений во время сборки; результат проверяется после записи.
Это компенсация в кооперативной среде, не общий атомарный снимок и не защита
от произвольного конкурентного writer. Ошибка записи/readback требует сверить
сохранившийся файл, не повторять запись вслепую. Перед зависимым действием сверить
источники, текущие сроки, отзыв и effects; видимый `asOf` не гарантирует свежесть.
При отказе сборщика достаточно отдельного текста/вопросов по direct records.

## Один вопрос и один ответ

Сборщик отказывается перезаписывать вопрос. Зафиксированный вопрос и основание сохраняются. После сохранения ответ становится readonly, повторное скачивание выдаёт те же bytes. localStorage — только удобство восстановления черновика в данном браузере, не контекст проекта и не источник приёмки. Изменение уже завершённого ответа переводит работу в ручной режим; старшие номера файлов не выбираются автоматически.

Прочитать явно возвращённый HTML **без исполнения**:

```sh
python3 -B tools/decision_view/receive.py project/handoff/example-answer.html --question project/handoff/example-question.html
```

Чтобы сохранить получение в контексте проекта, добавить `--record project/artifacts/process/example/response.json --handoff-ref "ссылка на сообщение человека, вернувшего ответ"`. Сначала сохранить полученный оригинал по правилам [project](../../project/README.md). Не выдумывать handoff reference; скачивание и наличие файла сами по себе не передача ответа.

Reader сверяет вопрос, точный текст, поля и доступные исходники; сохраняет `exactAnswer`, связи и digest, оставляя `interpretation:null`, `actions:[]`. Повтор того же ответа не создаёт эффект. Отличающийся ответ сохраняет прежнюю запись и устанавливает устойчивый `manualReview`; возврат старой копии его не снимает. Ручное разрешение конфликта и его основания записываются отдельно. Поддерживается один писатель, не конкурентные записи.

Прочитать свободные/частичные/условные слова в контексте и передать нужным existing owners — обязанность агента. Изменившиеся основания удерживают только зависимые действия. Digest не устанавливает личность человека и полномочие; helper не применяет решений и не заменяет G/X/E.

Цель — выпуск готового представления менее чем за минуту за счёт каркаса. Время анализа вопроса и получения оснований зависит от задачи; скорость сборки не доказывает минутный цикл для любого решения.
