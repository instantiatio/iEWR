# Компактный Decision View

Каркас для отдельного вопроса человеку: один автономный HTML с содержанием и полями ответа. Выбор и подготовка содержания — по [I](../../modules/interaction/DECISION_VIEW.md). Для достаточного ответа в разговоре файл не нужен. Вложения, сервер и браузерные библиотеки не требуются; материалы открываются по ссылкам.

## Быстрый пример

Из корня распакованного iEWR:

```sh
python3 -B tools/decision_view/build.py tools/decision_view/examples/question.json project/handoff/example-question.html
```

Открыть `project/handoff/example-question.html` обычным браузером как файл. Учебный пример создаст также ER-представление в `project/handoff/decision-view-materials/`. Ответ сохраняется кнопкой в `example-answer.html`; браузер выбирает папку скачивания. Вернуть этот файл в задачу явным сообщением. `page.html.in` — исходник каркаса, его не открывают как готовый результат.

Требования к сборке: Python 3.10+; для непосредственно связанных Markdown — также Node.js 20+. Marked включён в комплект с MIT-лицензией, установки пакетов не требуется. Готовые HTML читаются без этих инструментов и без сети. Для заполнения/скачивания ответа нужен JavaScript; сохранённый ответ читается и без него. Файловый режим проверяется в обычном браузере; поведение встроенного предпросмотра конкретного host может отличаться.

## Подготовить вопрос

В JSON указать `questionId` (предмет и редакция), `kind`, `question`, `subject`, `recipient`, `recommendation`, `waiting`. Пример показывает остальные поля. Три варианта `kind` меняют подачу оснований: `short-decision`, `comparison`, `acceptance`. Пустые разделы не добавляются. `options` может содержать любое число реальных альтернатив или отсутствовать — свободный ответ всегда доступен. `decisionRequired:false` не создаёт файл.

Дополнительно: `why`, списки `basis`/`limits`, `table` с `title`/`columns`/`rows`, `sections` с `title`/`text`, `details`, `materials`. Текст отображается как текст; произвольный HTML не исполняется. `synthetic:true` помечает учебные данные. Существенные ограничения, рекомендация и последствия остаются на основной странице. Стараться уложить простой вопрос примерно в один экран; число экранов не заменяет достаточность содержания.

Числовые `parameters` имеют `id`, `label`, `unit`, `min`, `value`. Изменённые условия сохраняются точно, но каркас не пересчитывает модель: зависимый расчёт выполняется отдельно. Если допустим вариант пересчёта, его ID задаётся как `parameterChangeChoice`; иначе при изменении параметров использовать свободный ответ.

Для материала нужны `path`, `filename`, `title`, `revision`, `role`, `linkPurpose`; необязательный `sha256` фиксирует ожидаемый исходник. Локальный путь считается от JSON, а в готовом HTML пересчитывается относительно вопроса. Отсутствующий файл или несовпадающий digest останавливают сборку. `role:decision-evidence` показывает предел независимой проверки при недоступном материале. Внешние HTTP(S)-ссылки сохраняются без загрузки и проверки.

## Дополнительные представления

Сначала выбрать достаточный основной каркас. Если отношения, геометрия или сценарии в нём плохо различимы, добавить отдельное представление с конкретным вкладом и ссылкой с основной страницы. Не создавать универсальную библиотеку приложений к каждому вопросу.

| Вход в `materials` | Подготовка |
|---|---|
| Локальный `.md` | Статический HTML для чтения; исходник сохраняется. Глубокие MD-ссылки помечаются «исходник MD», рекурсивной конвертации нет. |
| Локальный `.er.json` | Проверка структуры модели и ER-схема SVG внутри автономного HTML: сущности, поля, PK/FK/UK, кратности, таблица связей, масштаб/прокрутка. |
| `.zip` | Сначала раскрываются имя и известный размер, затем отдельная ссылка скачивания. |
| Готовый HTML, SVG, PDF и другие материалы | Обычная ссылка; пригодность формата проверяет автор. |

Производные страницы имеют имя с digest и переиспользуются при совпадении содержания. Они не вложены в вопрос. Если вопрос перенесён и относительная ссылка больше не работает, рядом остаётся сообщение с точным именем файла/редакцией и просьбой запросить материал у Developing Engineer. Браузер не всегда позволяет автоматически установить отсутствие локального файла; условное сообщение не выдаёт предположение за факт.

Markdown reader показывает заголовки, списки, таблицы и код. Raw HTML экранируется, изображения заменяются подписями; Mermaid внутри Markdown остаётся кодом. Если изображение или диаграмма меняют решение, дать отдельное подготовленное представление. Автоматического распознавания ER из текста, SQL или Mermaid нет.

ER-модель имеет `schema:1`, `title`, `revision`, `entities` и `relationships`; точный пример — [orders.er.json](examples/orders.er.json). У сущности уникальный ASCII `id`, необязательный `label`, атрибуты `name`/`type`/`keys`. В связи нужны `from`, `fromAttribute`, `to`, `toAttribute`, `fromCardinality`, `toCardinality`; допустимы `1`, `0..1`, `1..*`, `0..*`, `?`. Кратность у конца означает число объектов этого конца на один объект противоположного. Неизвестное указывать `?`. Неподтверждённое не достраивать по догадке.

ER renderer ограничен 50 сущностями, 100 полями на сущность и 200 связями; это предел входа, не гарантия читаемости плотного графа. Для сложной модели выделять нужный фрагмент или использовать другое представление. Он не подключается к БД, не проверяет SQL/миграцию/смысл ограничений. Самостоятельная команда: `python3 -B tools/decision_view/er.py model.er.json diagram.html`.

## Один вопрос и один ответ

Сборщик отказывается перезаписывать вопрос. Зафиксированный вопрос и основание сохраняются. После сохранения ответ становится readonly, повторное скачивание выдаёт те же bytes. localStorage — только удобство восстановления черновика в данном браузере, не контекст проекта и не источник приёмки. Изменение уже завершённого ответа переводит работу в ручной режим; старшие номера файлов не выбираются автоматически.

Прочитать явно возвращённый HTML **без исполнения**:

```sh
python3 -B tools/decision_view/receive.py project/handoff/example-answer.html --question project/handoff/example-question.html
```

Чтобы сохранить получение в контексте проекта, добавить `--record project/artifacts/process/example/response.json --handoff-ref "ссылка на сообщение человека, вернувшего ответ"`. Сначала сохранить полученный оригинал по правилам [project](../../project/README.md). Не выдумывать handoff reference; скачивание и наличие файла сами по себе не передача ответа.

Reader сверяет вопрос, точный текст, поля и доступные исходники; сохраняет `exactAnswer`, связи и digest, оставляя `interpretation:null`, `actions:[]`. Повтор того же ответа не создаёт эффект. Отличающийся ответ сохраняет прежнюю запись и устанавливает устойчивый `manualReview`; возврат старой копии его не снимает. Ручное разрешение конфликта и его основания записываются отдельно. Поддерживается один писатель, не конкурентные записи.

Прочитать свободные/частичные/условные слова в контексте и передать нужным existing owners — обязанность агента. Изменившиеся основания удерживают только зависимые действия. Digest не устанавливает личность человека и полномочие; helper не применяет решений и не заменяет G/X/E.

Цель — выпуск готового представления менее чем за минуту за счёт каркаса. Время анализа вопроса и получения оснований зависит от задачи; скорость сборки не доказывает минутный цикл для любого решения.
